M00.3 y Fase 00 permanecen cerrados. M01.1 cerrado tras revisión APPROVE_WITH_FOLLOWUPS, único hallazgo F-4 corregido y gates verdes. R-011/R-012 resueltos; R-016/R-017/R-018 siguen como requisitos de fases posteriores, no hallazgos bloqueantes de M01.1. Ninguna excepción de gate está aprobada de forma implícita.

- R-014 — Cerrado en B01-01 (`4bf3e58`): reemplazadas expectativas derivadas de la implementación por tabla independiente que cubre los 49 pares; semántica de tarea/intento/efecto y aprobaciones documentada en contrato.
- R-015 — Baja, mitigado por evaluación B02a-01: Node local 24.13.0 difiere del 24.19.0 de CI. Ambos ejecutaron gates completos en Windows x64; se elige 24.19.0 por SQLite parcheada. No acredita nueva CI Linux ni actualización global; el manifest aún permite versiones antiguas y debe restringirse/verificarse antes de persistencia real.
- R-016 — Media: el lifecycle es validación pura de adyacencia. La ruta `uncertain -> failed -> queued` sólo es admisible tras reconciliación; `awaiting_approval -> succeeded` requiere evidencia y aprobación cuando corresponda. Los futuros servicios deben imponer esas precondiciones y conservar el historial de intentos. Los tests actuales no acreditan enforcement, permisos, reconciliación ni durabilidad.
- R-017 — Media, seguimiento B02: los parsers B01-02 validan estructura/versiones, no veracidad de declaraciones de efectos, existencia/hash de blobs, correlación entre eventos ni unicidad/idempotencia de IDs. Persistencia/aplicación deben conservar el manifest por run/bloque, correlacionar intentos y verificar evidencia antes de reutilizar resultados; requieren tests de integración/fallos.
- R-018 — Media, antes de logs/efectos: los diagnósticos de validación no interpolan datos de entrada, pero un mensaje de ejecución o blob válido puede contener secretos. El productor debe redactar antes de guardar/loguear; no hay redactor implementado en B01-02. La frontera de los parsers son datos JSON decodificados; no son un sandbox para getters/proxies u otros objetos JavaScript hostiles.
- R-019 / F-4 — Baja, cerrado: constantes exportadas del lifecycle mutables en runtime alteraban la validación global. Confirmado con tres tests rojos; congeladas lista, arrays y tabla mediante Object.freeze. Regresión y compatibilidad de tipos desde dist verdes, suite 62/62. Revisión APPROVE_WITH_FOLLOWUPS registrada; sin hallazgos bloqueantes restantes.
- R-020 — Alta, gate B02b: SQLite 3.50.4 del Node instalado está afectada por WAL-reset (fuente oficial enlazada en el spike), carrera rara de write/checkpoint entre conexiones en distintos threads/procesos. Pruebas verdes no descartan ese defecto. Node portátil 24.19.0/SQLite 3.53.3 verificado resuelve la elección; exigir runtime parcheado antes de datos reales, sin cambiar globalmente Node en B02a. node:sqlite es release candidate en 24.19, no API estable definitiva.
- R-021 — Media: DatabaseSync y busy timeout bloquean el hilo llamante; 75 ms configurados tardaron ~133–142 ms en muestras locales. Usar worker dedicado y un escritor; mensajes de cancelación no interrumpen una llamada síncrona. Los tests sólo prueban aislamiento/locks, no backpressure, deadlines de producto ni retry seguro.
- R-022 — Media: SIGKILL verifica crash de proceso, no pérdida de alimentación/SO. NORMAL puede perder commits en esos escenarios; FULL seleccionado, sujeto a garantías reales de filesystem/hardware. Falta validar backups/checkpoints productivos en su tarea; usar WAL en filesystem local. Benchmark local sin SLA; no se infiere durabilidad del kernel a partir del spike.
