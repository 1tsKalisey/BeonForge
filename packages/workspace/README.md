`state=confirmed`/receipt son historia durable; `current` es validación actual. Clean compara tracked con commit de creación (bytes/índice/modos Git), HEAD detached esperado y pins válidos; modified incluye edit/delete/staging. Drift = HEAD/checkout/identidad divergentes; invalid incluye ausencia, enlaces inseguros o verificación fallida. Marker ausente/inválido -> uncertain. Fuente/reserva inválida o permisos denegados pueden producir error tipado. Ninguna edición sustituye el receipt.

Untracked/ignored están fuera de la validación posterior: sin enumerar sus nombres/directorios ni leer contenidos privados. Git usa untracked-files=no e ignore-submodules=all; sólo se leen paths tracked esperados/índice. Nuevo staged -> modified. Creación inicial sí exige inventario exacto. Clean no promete directorio estéril ni concede permiso para herramientas o consumir extras. HEAD inicial sólo metadata; cada componente tracked se valida antes de leer y de Git status, sin seguir junctions/symlinks.

CLI worktree inspect/create: exit 0 sólo confirmed+clean, 2 para cualquier otro reporte (incluido prepared/modified), 1 para error/permisos. Create despachado sigue denegado aunque el receipt exista; no override, retry ni limpieza. Otro uso con drift/invalid/uncertain requiere decisión explícita autorizada fuera de esta tarea.

Demo: pnpm.cmd build y pnpm.cmd --filter @beonforge/workspace exec vitest run -t B0303. Proyecto Git temporal representativo TypeScript con package.json, tsconfig, README, src/app.ts y gitignores raíz/anidado; bytes/OID/Git check-ignore, original intacto, extras privados ignorados y edición/reinicio con receipt original. ## Worktrees — B03-02

Actualización focalizada: P3-1 (historia durable) y P3-2 (atributos) verificados independientemente, APPROVE_WITH_FOLLOWUPS. Check-attr ahora usa --stdin -z --source=<OID> con nombres NUL y EOF explícito, sin nombres en argv. Entrada/salida limitadas a 1 MiB, timeout Git 5 s; errores de spawn/stdin sanitizados git_failure y límites git_limit, sin spawnargs/causa/rutas de entrada en error. Backpressure queda acotada por el buffer de entrada máximo; fin/error de escritura y cierre de proceso manejados sin retry. Mantiene la política de atributos y no altera historia/current ni grants. Pruebas de 500 nombres largos en Windows y atributos hostiles; compatibilidad .gitignore/.git* aún pendiente.

Auditoría APPROVE_WITH_FOLLOWUPS recibida, sin P0–P2. Correcciones P3 pendientes de revisión focalizada: confirmed.json v1 wx/write/fsync enlaza intención y receipt CAS original tras verificar. Inspect conserva ese receipt; state=confirmed es historia, current=clean/modified/drift/invalid es estado actual. No concede permisos; create rechaza todo dispatch previo. Marker ausente/inválido/truncado o corte previo a su persistencia -> uncertain, sin reparación/retry/limpieza. CAS huérfano no sustituye el marker. No se acredita power loss de directorios Windows.

Preflight: check-attr --source al OID exacto, salida NUL acotada y validada para working-tree-encoding/filter/text/eol/ident, info/attributes incluido. Rechaza todo valor distinto de unspecified (incluido unset), antes de reserva y otra vez antes de dispatch. Sin ejecutar filtros; atributos globales/system desactivados, entorno aislado/R-039 conservados. Salida no fiable -> fallo cerrado.

**Compatibilidad parcial:** B03-03 permite .gitignore regular exacto; otros .git* y nombres no ASCII, >512 archivos, blobs/salida >1 MiB, total >32 MiB o profundidad >16 siguen rechazados. No acreditar compatibilidad general antes de ampliar y probar esos límites.

API: prepareWorktree(projectRef, commitOid, executionRoot, policy, store) publica intención v1 en CAS y reserva un padre exclusivo; createWorktree(intentRef, policy, store) realiza una única tentativa; inspectWorktree(intentRef, policy, store) verifica o recupera evidencia sin repetir efectos. WorktreePolicy añade executionRoots, metadataWriteRoots y storageRoot privado real del store. Store y policy son configuración confiable del operador, no datos concedidos por un descriptor.

CLI (build actual, mismo --storage de project register):


Create emite primero una línea prepared con intentRef y después el reporte final. Conservar la referencia; no hay catálogo. Para origen linked worktree añadir --git-root y --common-root de B03-01. Escritura de gitdir/common-dir y ejecución se autorizan separadamente; las autorizaciones de lectura no bastan. Destino siempre checkout bajo un padre mkdtemp nuevo; no permite elegir/reutilizar un checkout existente.

Protocolo: intención CAS antes del efecto Git, dispatch.json exclusivo/fsync con SHA de intención antes de add. Marcador no es evento SQL ni transacción distribuida. Prepared significa no despachado; pending, operación activa en este proceso; uncertain, despacho sin resultado completo comprobable; confirmed, HEAD detached/OID/lock de propiedad/índice/bytes/inventario verificados y recibo CAS v1 enlazando intención y descriptor del nuevo proyecto. Un dispatch ya existente impide toda repetición, incluso tras reinicio; inspección puede confirmar una creación acabada sin recibo. Cortes antes de publicación de intención pueden dejar sólo reserva huérfana, sin efecto Git; no se limpia automáticamente. No hay exactly-once, GC ni recuperación automática de parciales.

Materialización: git worktree add --detach --no-checkout --lock al OID local exacto con hooksPath vacío privado. Luego blobs como bytes mediante escrituras wx/fsync, y read-tree sólo para índice propio; no checkout, filtros, conversiones de atributos ni submódulos. Git y PATH confiables, entorno aislado, sin shell/red/force/fetch; límites Git 5 s/1 MiB. Revalidación de fuente, permisos, reserva y metadata de destino antes de mutaciones. Sólo entradas regulares 100644/100755, nombres ASCII seguros portables (sin .git* salvo .gitignore regular exacto, enlaces, gitlinks, nombres Windows reservados ni colisiones de mayúsculas); 512 archivos, 16 componentes y 32 MiB totales, cada blob dentro del límite Git. Estas restricciones incluyen .gitattributes/.gitmodules: fallar cerrado hasta ampliar con evidencia. El checkout original puede estar dirty; no se copia su estado. Cambian únicamente los metadatos comunes necesarios para worktrees (y timestamps de directorios administrativos), no su HEAD/rama/índice/config/archivos.

Raíces privadas: POSIX exige propietario/modo privado para executionRoot; Windows requiere ACL privada del operador como el store. Se rechazan solapamientos, junctions/symlinks, CAS/backups identificables; la API debe recibir storageRoot auténtico del ArtifactStore. No es sandbox de procesos, autenticación contra el dueño ni liderazgo multiproceso; exclusión de common-dir intraproceso y wx por intención, uso exclusivo del repositorio por el operador. Los worktrees quedan locked intencionadamente, sin API de unlock/remove/prune. Revert de código conserva datos/worktrees; reparar/borrar parciales requiere revisión y autorización explícita. Tests SIGKILL prueban crash de proceso, no pérdida eléctrica ni fsync de directorios portable en Windows.

## CLI

Con Node 24.19.0/SQLite 3.53.3 aprobados, Git instalado y build actual:

```powershell
pnpm.cmd build
pnpm.cmd --filter @beonforge/workspace cli project register --root C:/proyectos/app --storage C:/BeonForge-private
pnpm.cmd --filter @beonforge/workspace cli project inspect --allow-root C:/proyectos/app --storage C:/BeonForge-private --ref <sha256> --bytes <byteLength>
```

`--storage` es un directorio privado **existente**, absoluto y separado de proyectos y metadatos autorizados. Ambas operaciones usan `projects.sqlite` y su ArtifactStore `projects.sqlite.artifacts` dentro de ese directorio. No existe catálogo: conservar la referencia completa y el mismo almacenamiento permite inspeccionar desde otro proceso/reinicio. Inspect no inicializa una DB ausente. POSIX exige propietario actual y modo sin permisos de grupo/otros; en Windows, el operador debe asegurar ACL privadas como en la persistencia existente. La API recibe un ArtifactStore confiable ubicado fuera de los proyectos; el CLI aplica la separación.

Para un worktree añadir en ambas operaciones `--git-root <gitdir-exacto>` y `--common-root <common-dir-exacto>`, obtenidos por el operador. Son autorizaciones separadas para metadatos; ninguna concede acceso a otros checkouts. `--allow-root` de inspect puede repetirse. Registro e inspección revalidan permisos; el descriptor no los otorga.

## Identidad y límites

- Descriptor JSON v1: raíz canónica, gitdir, common-dir, pins dev/ino/tipo y dos IDs SHA-256. pathId identifica la ruta canónica; repositoryId combina ruta y objeto físico del directorio común. Worktrees comparten repositoryId y tienen pathId distinto. Sustituir la raíz, `.git`, config o enlaces físicos de worktree requiere nuevo registro. No es identidad global de Git entre clones o tras mover el repositorio.
- HEAD/rama/índice pueden cambiar normalmente. Se informa HEAD nullable, detached/unborn, número de cambios tracked y presencia de gitlinks. No se persisten snapshots de inspección, contenidos, URLs remotas, configuración o nombres de archivos. El descriptor contiene rutas privadas: proteger el CAS y las referencias.
- Rutas locales absolutas; rechazo de traversal, symlinks/junctions, UNC/device paths y ADS en Windows. Permisos por parentesco de rutas canónicas, sin prefijos textuales. Identidad física no disponible (ino=0) falla cerrado. Se contrastan identidades antes/después de Git, bajo raíces y ancestros privados no modificables por actores hostiles. Esto no es sandbox contra un propietario privilegiado concurrente ni snapshot atómico de HEAD/índice.
- Allowlist Git fija, argv separados, sin shell, pager ni locks opcionales. Config global/system y variables Git heredadas aisladas; fsmonitor, atributos/excludes externos y lazy fetch desactivados. No se cambia safe.directory. Includes, filtros, continuaciones de configuración, alternates y git-dir separado que no sea worktree se rechazan; no se ejecutan proveedores, hooks ni comandos externos definidos en configuración del repositorio.
- Config y config.worktree se validan primero con el parser oficial `git config --file <ruta> --no-includes --list --name-only -z`, bajo las mismas protecciones y límites. Se rechazan claves include/includeif/filter por su sección normalizada, incluidas mayúsculas, subsecciones y encabezados contiguos. --no-includes limita el parser explícito, pero el descubrimiento inicial por -C root todavía puede cargar includes externos (R-039 pendiente). Errores de parsing/salida inesperada fallan cerrado antes de status; el rechazo de continuaciones y los pins físicos se conservan.
- Sólo se leen pequeños archivos de configuración/punteros (256 KiB) y metadatos de identidad; se revisan entradas de objetos/refs para rechazar enlaces, sin leer sus blobs ni explorar otros checkouts. Límite 10 000 entradas por validación. Cada comando: 5 s y 1 MiB stdout+stderr; ante exceso, git_limit, sin retry. Repositorios mayores pueden rechazarse: ampliar sólo con evidencia. Git status puede leer archivos tracked para calcular cambios; no enumera untracked/ignored y usa ignore-submodules=all. ls-files detecta gitlinks sin abrir submódulos. No se implementa lectura/indexación del código.
